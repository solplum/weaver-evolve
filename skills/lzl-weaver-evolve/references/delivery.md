# 结果怎样交付给用户

执行结束、生成报告或回复用户前读取。交付应让用户直接判断成果能否使用、重要发现有什么影响、是否需要自己作决定。

## 从结果开始

先写本轮实际改变及其用途。多项结果按用户关心的主题合并，不按扫描步骤排列。新增文章要说明保存了什么可复用内容，更新旧记录要说清变化；数量本身不代替价值。

有必要的遗留在开头结果中一并说明，不能到结尾才透露核心更正尚未完成。推送等附带操作用一句状态交代，避免挤占知识整理的主线。

合并多个结论时，保留共同的对象与核对范围。“权限、统计、分析等均已覆盖”这类宽泛列举，如果没有解释或可用入口，可以直接省略；不要为显示工作面而放大结论。

例如，一次有本地写入的整理可以直接说：“已将项目旧权限说明改为你确认的新规则，并合并两条重复笔记。现有方法文档已有‘先检查最小输入’的步骤，没有再建一篇文章。另有一段外部说明无法访问，尚未核对。”具体内容取自本轮事实，不照抄例子凑结果。

## 给出可用入口和清楚含义

- 指向实际新增或更新的文章、文档或记录，让用户能直接打开；链接不能只通向候选 JSON 或内部证据。输出环境限制链接形式时，在允许的位置提供可用的阅读副本或明确入口。
- 审查已有记录时，同样给出有用的复核入口，不让用户根据代码样式路径自行寻找文件。没有变化的简单审查，结论与影响判断的例外足够，逐项核对记录不必占据正文。
- 重要更正包括原记录、现在应如何理解、实际改了哪里。判断依据、当前实现和部署状态分开说明；没有核验的层次不能混为已完成。
- 更正只保存为提案时，直接说“更正提案已保存，正式摘要尚未更新”；维护进程、接口限制等细节放在提案里，仅在用户确实需要处理这些条件时展开。
- 面向该任务的读者解释术语。例如，先说明“平台没有给出具体员工时，记为平台调用”，再补充仅适用于获授平台代查权限的凭据；不要把作用域条件删掉换取表面简短。
- 正文通常不需要原始消息 ID、内部状态英文、游标、读取页数或候选分类统计。用户要查证时提供准确来源；材料较多时附一个可选证据入口。

长表只在便于比较时使用。独立成果用短段落或清楚的链接列表；不要把来源、约束、实现状态与多层例外挤进同一单元格。

范围通常一句话即可。快照事件、页数、完整性证明与未改文件清单放在可选证据中；只有遗漏范围会改变结论时，正文才展开说明。产物已存在且没有修改，也可以是清楚的整理结果，不必再造一篇笔记。

## 说清真正未完成的部分

留下一项待处理，应能解释具体缺口和已经做过的核对。例如：“已搜索现有索引和两个授权目录，未找到旧文的原始版本；需提供原文件才能恢复链接。”不要仅写“待核对”“待归位”“通过拥有者入口处理”。

能在本轮继续查证的工作先做完。已有记录覆盖的内容无需重复写；只属于其他项目的未来实施，关联到其已有任务，不自动要求用户再次批准。需要用户选择时，给出具体差异、建议及影响，其他不依赖该选择的工作继续完成。

用户只要求审查时，指出发现及建议，明确未实施即可；没有新内容时，简短说明已覆盖的范围和无需修改的原因。把逐项证据保留在核对记录，正文不再展开一张带源事件编号、行号和覆盖计算的审计表。不要为填报告新增笔记、待办或确认问题。

无变更的简单结果可以是一个自然段，例如：“现有[构建说明]已准确记录你确认的包管理方式，不需要再建一条规则。讨论中的容器方案尚未采用，仍按现有方式执行；本轮只完成审查，没有改文件。”实际对象和范围以本次证据为准，不能照抄这个例子。

## 检查读者是否还要替你归纳

读完开头应能知道这次得到了什么，以及最重要的限制；打开成果链接应能看到对应内容。每个遗留应有明确下一步，读者不必从内部术语和统计中推断哪些工作已完成。

保留必要的范围和不确定性，一处说清即可。简短不等于省略关键结论；详细也不等于把执行记录原样搬进正文。
