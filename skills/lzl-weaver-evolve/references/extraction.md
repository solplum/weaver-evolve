# 知识提炼与价值判断

提取候选或难以判断是否值得保存时读取本文件。

## 从材料到知识

保留能改变下次判断或执行的内容，压缩掉无关过程。每条候选应能回答：谁在什么条件下可以使用它、依据是什么、下次会因此采取什么不同的行动？没有这样的用途就不必落盘。

| 材料 | 可提炼的知识 | 需要保留的边界 |
|---|---|---|
| 一次成功交付 | 经验证有效的工作流和关键检查 | 项目条件、成功证据，不能声称普遍有效 |
| 用户明确纠正 | 偏好或判断边界 | 原意、适用对象；一次明确纠正即可有价值 |
| 方案选择与放弃 | 决策及其取舍依据 | 当时约束、何时需要重新评估 |
| 已定位的事故 | 根因与有效预防措施 | 区分证据充分的根因、相关线索和猜测 |
| 两项目的相似问题 | 可能共享的约束或方法 | 核对是否同一原因，表面相似不能直接泛化 |
| 调用脚本或改了若干文件 | 通常留给任务记录／版本历史 | 只有形成可复用方法时才进入知识库 |

复用价值来自明确性、影响和适用性，重复出现只是证据之一。不要设置“至少发生 N 次才能保留”的门槛；也不要只扫描报错和失败，忽略成功经验、决策及用户纠正。

## 候选最小记录

- 主张及适用条件：一句可独立更新的知识。
- 来源定位：优先用稳定事件 ID、提交或内容版本加锚点；可改写文件的行号只作辅助，不能单独作为长期定位。保留时间，区分用户表达、工具结果与助手推断。
- 依据及复用价值：已验证什么，下次用于什么。
- 建议动作：新增、更新、合并、排除或待核实；具体落点及已知关联位置。

这份记录用于本次分析。进度文件只留来源引用、处理状态和简短原因；完整知识写入合适的知识落点，私密聊天和凭据不复制进技能状态。

## 判断例子

- “这次离线演练通过”只证明该次演练；没有设备验证时不能沉淀为“设备环境已验收”。
- “以后所有项目优先复用现有依赖”是明确跨项目原则；“这个项目暂不升级依赖”是项目例外。
- 一次有明确前提、结果可核对的成功排查，可以形成方法；未经验证的助手总结继续待核实。
- 用户从 A 改用 B，保留原因和适用范围；不要同时保留“默认 A”“默认 B”让下次自行猜测。
- 推断可能有价值时交付可核对的候选及最小验证问题；信息下沉到项目并不会把推断变成事实。
