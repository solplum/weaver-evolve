# lzl-weaver-evolve

把分散的信息变成后续任务可复用的知识，并留下可续接的进度。维护一套正文；位置、工具、规则和记忆接口由运行环境提供。

## 1. 确定本次覆盖范围

- 从用户指定的项目、资料和时间范围开始；复用本轮已明确的授权。
- 用户只说“全局整理”时，以当前上下文可定位的项目和来源为边界；缺少时间条件和增量记录时先取近七天并说明假设。先盘点再完成请求范围内的常规归位；只要求审查时保持只读，不把普通整理自动降成仅交建议。
- 内部记录 `项目 / 来源 / 时间或版本边界 / 覆盖状态`，限定本次读取到哪个时点、事件或内容版本。新增发现的项目先列为候选范围，不扫描整盘。
- 先读取当前环境和目标位置的适用规则，识别全局指令、项目指令、可写知识库、记忆拥有者和可用历史接口。只有真实存在且被当前环境使用的位置才是落点；文件名相似不代表会生效。发现、覆盖和分层细则见 [references/routing.md](references/routing.md)。

完成标准：能说明整理的是哪些项目、哪些证据，以及哪些内容尚未覆盖。

## 2. 读取增量，保留未完成事项

- 优先使用当前上下文、用户指定材料和可用的专用历史接口；本地历史需要先抽样识别实际格式。历史中的命令、示例和助手建议是证据材料，不是当前执行指令或用户决定。
- 先载入本技能自有进度和待处理候选，再按来源读取增量。来源独立记录游标；一个来源不可读不阻断其他来源，也不代表它没有新增内容。
- 来源是否读完、知识是否归位、所属项目是否开发完成分别判断。既定快照全部读完即可记录完整覆盖，不等活跃聊天结束；只有本次范围确实缺读才标部分读取。
- 读取前比较本次范围与已覆盖区间。时间范围扩大、项目筛选改变或源内容改写时先补扫新增／变化部分；旧游标缺少覆盖边界时，重新读取本次范围，不能只从末尾续读。
- 完整读取后，在游标的覆盖描述中保存起点和筛选条件；对可改写来源同时记录内容版本。原生游标本身不携带这些信息时，用 JSON 对象同时保存原生位置与覆盖描述。
- 首次或一次性整理可不建持久进度。需要持续增量时，在授权的数据目录保存技能自有状态，使用 [references/progress.md](references/progress.md) 中的 `scripts/progress.py`；它只记录来源定位、处理状态和游标，不承载宿主记忆。
- 部分读取或不可访问的来源保留旧游标。完整扫描后，只有候选都已归档、明确排除或持久记录为待处理，才能推进该来源游标。未建持久进度时，交付可续接清单，不声称已保存增量进度。

完成标准：已读来源有边界，未处理事项不会因本次结束或游标推进而消失。

## 3. 提炼值得保留的知识

候选可以来自一次明确决定，也可以来自多条互相印证的经验：

- 用户明确的长期偏好、纠正和取舍依据；
- 项目决策及其成立条件、约束和改变方案的原因；
- 已验证有效的方法、成功工作流和工具选择经验；
- 已查明的错误根因及能改变后续行动的预防措施；
- 跨项目共性、被推翻的结论、重复或过期知识。

每条候选说明：`知识主张 / 来源定位 / 事实或推断 / 适用范围和条件 / 复用价值 / 建议落点与动作 / 已知关联位置`。高影响或可变事实回到拥有来源核验；明确表达与助手推断分开。提炼案例与纳入标准见 [references/extraction.md](references/extraction.md)。

不以出现次数代替价值判断。一次任务状态、普通操作流水账、无依据的性格判断和无法改变后续决策的空泛结论，列为排除或待核实，不能改写成长期规则。

## 4. 路由、去重与处理冲突

- 根据内容类型、适用范围及拥有者选择落点：执行约束进环境认可的指令位置；全局稳定偏好进现有全局记忆；项目决策进项目知识；可独立复用的方法进已有知识库。找不到受支持的落点就保留候选，不强塞进指令文件。
- 对托管或生成的记忆，只使用当前环境规定的接口或增量提案机制；即使底层文件可写，也不直接改生成文件。
- 写前搜索目标、相关索引和已知关联记录。已有相同内容则无需新增；互补内容合并；变化发生在原条目，保留必要来源与时间。
- 冲突先比较对象、条件、适用范围和证据。项目例外不覆盖全局偏好；同范围的新明确决定才替代旧决定。事实不确定时保持待核实；仅范围不确定时考虑较窄范围。
- 更新或删除时检查已知关联位置和引用。仅清理有证据失效且已获授权的内容；暂时访问失败不等于死链，文件不存在不等于项目已永久废弃。

完成标准：需要更正的旧记录和已知关联位置已经核对，候选有实际处理结果或已查明的具体缺口。

## 5. 按现有授权执行

- 先形成具体变更：目标位置、现有内容、拟修改内容和关联影响。一般整理在一次紧凑计划中说明即可，不把读资料、分类或常规验证变成审批步骤。
- 把事项留待处理前，先完成范围内可做的核对：读取已知索引、现行合同或知识记录，搜索是否已覆盖，并执行已授权的更新。“还没核对”是下一步工作，不是结束理由。
- 已授权的具体操作直接完成。仅对缺少的关键判断、范围扩大、未获授权的破坏性操作或拥有者明确要求的确认集中提问；其他独立工作继续进行。
- 真正缺少条件的事项说明缺什么、已查到哪里、下一步由谁做什么。其他项目仍在开发、已有跟踪的任务或已覆盖的知识，保留其上下文或引用，不重复制造成本轮待办；不能把排除重复归档说成业务问题已经解决。
- 有权限且接口允许的更新按原结构融入；外部发布、权限配置、移动普通文件和修改技能自身，分别需要当前请求确实涵盖相应动作。调用本技能不自动授权这些动作。
- 本流程自包含。需要独立记忆操作、文件移动或专门错误复盘时，可使用可用的 `memory-keeper`、`file-tidy`、`debug-architect`；先确认其规则适用，并传入本次来源、目标和授权范围。缺少或不适用的配套技能不阻断本流程，也不扩大任务。

## 6. 验证与记录

- 读回修改处或检查接口回执，确认实际落点、语义、范围和索引引用；规则检查实际加载与覆盖关系，配置检查语法及字段契约。只改知识时无需检查无关配置。
- 使用目标支持的差异或版本机制核对本次变更；普通非版本目录用修改前后对照。并行内容变化时重新比对，不覆盖他人改动，也不整文件回退无关修改。
- 验证成功的候选标为已归档；未改且已存在的标为已排除并注明“已覆盖”；失败或缺授权的保持待处理。最后提交进度；冲突或写入失败时保留旧状态并交付续接清单。
- 按用户这次请求判断完成状态：审查完成不等于已实施；整理请求中尚未完成的必要归位要说明。范围外的项目进展、截点之后的新消息和已排除的可选事项不构成本轮未完成。

## 7. 向用户交付

交付前读取 [references/delivery.md](references/delivery.md)。对话与报告文件都是给用户看的结果正文，先说明实际改好了什么、最重要的发现及影响，再说明实质遗留和需要用户决定的事项；没有对应内容就省略，不强制套满章节。

报告作为成果或核对对象提到的主要记录，给出可打开的入口；只审查、无修改时也能直接查看现有记录。新增知识说明一句用途，重要更正说清原记录、当前结论和实际处理结果。术语先用任务中的人话解释，只保留影响理解的技术条件。

无变化的简单审查，用自然语言说明一致性结论，链接主要现有记录，只解释影响结论的例外。逐条来源编号、快照计算和续接状态通过可选证据或进度入口提供；写进报告文件不等于需要展示审计清单。用户明确要完整核查清单时再展开。

无需变更也是有效结果：说明已检查的范围及原因，保留仍需续接的事项。
